# 02 Codebase, build and CI

> This page is the map of the repository as something you build and check. It covers the Cargo workspace that produces `hfnode` and its libraries; the firmware builds that sit beside that workspace but outside it (the keyer box today, the decoder box of PR #30, and the parked UV-K1 handheld image); the 3D-printed enclosure model; the compiler each build uses; the commands; the environment variables the tests read; and every job of the GitHub Actions workflow with what it proves. It also explains how the keyer box's firmware file (a UF2) is built and identified, and why the file flashed onto a box must be CI's artifact with the SHA-256 that the safety audit published. Everything here lives at the repository root: `Cargo.toml`, `crates/`, `firmware/`, `hardware/`, `deploy/` and `.github/workflows/ci.yml`.

Terms used on this page, in plain words (the full list is [17 Glossary](17-glossary.md)):

- **CW**: Morse code sent by switching a radio's transmitter on and off. **Keying** is that switching; a **key line** is the two-wire switch input on a radio that does it.
- **Keyer box**: a Raspberry Pi **Pico 2** board (its chip is the **RP2350**, two Arm Cortex-M33 cores) running this repository's firmware on Robin's bare-metal OS **rustos**. It closes a radio's key line on `hfnode`'s command, within limits of its own. See [08 Keyer box: firmware](08-keyer-box-firmware.md).
- **UF2**: the file format the Pico 2's boot ROM takes. Hold the board's **BOOTSEL** button while plugging it in, it appears as a USB drive called `RP2350`, and a `.uf2` file copied onto it is written to flash.
- **ELF**: the executable file the Rust linker writes; `uf2.py` turns it into the UF2.
- **`no_std`**: a Rust crate that does not use the standard library, so it can run on a microcontroller with no operating system.
- **IC-7300** is an ICOM radio that `hfnode` controls over **CI-V**, ICOM's serial command protocol; the **mock IC-7300** is a byte-level simulation of it used by the tests. **UV-K1** is a Quansheng handheld radio; **NR7Y** is the community CW firmware for it.
- **Artifact**: a file a GitHub Actions run keeps for download.
- **KB-9, KB-13**: item numbers in the safety audit's report (project files, `audit/report.md` §1), cited by comments in the code.
- **PTT**: push-to-talk, the line that puts a radio on transmit. The keyer box has a PTT output for an FM handheld.
- **GP16, GP17, GP18**: the RP2350's GPIO (general-purpose pin) numbers 16 to 18: the keyer box's key output, PTT output and tone output. GP16 is pin 21 on the Pico 2's header.
- **SIO, `GPIO_OUT_CLR`**: the SIO is the chip's single-cycle I/O block; writing a bit to its `GPIO_OUT_CLR` register drives that pin low.
- **PWM, ADC, DMA**: pulse-width modulation (how the box makes its tone), the analog-to-digital converter (how the decoder box samples audio), and direct memory access (hardware that copies data with no processor instructions).
- **Vector table, Thumb bit, IMAGE_DEF**: the vector table is the list of start-up and exception addresses at the start of an Arm image; the low bit set on a code address marks Thumb code, the only kind a Cortex-M33 runs; IMAGE_DEF is the block the RP2350's boot ROM must find before it starts an image.
- **FPU, coprocessor**: a coprocessor is an extra instruction set that each core turns on or off, such as the floating-point unit (FPU) and the RP2350's GPIO coprocessor, which can change pins without a store.
- **HOTP, HMAC**: a one-time code computed from a counter with a keyed hash (HMAC); here, the field operator's letter codes.
- **SNR**: signal-to-noise ratio, here of the CW signal in a 2500 Hz bandwidth.
- **Sidetone monitor**: `hfnode` listening to the radio's headphone audio for the radio's own keying tone, to confirm the radio really keyed.
- **AGN, DE, station ID**: `AGN` is the field operator's "say again"; `DE <call>` means "this is" and gives the station identification (ID) the law requires.
- **`17 FF`**: the CI-V command that stops the IC-7300's CW keyer mid-message: command `17` sends CW text, and the data byte `FF` means "stop" ([`crates/civ/src/ic7300.rs:135-138`](https://github.com/robinonsay/cw-message-gateway/blob/44185fa9a00369c379d9d8af40ca307e3867e860/crates/civ/src/ic7300.rs#L135-L138), sent at [`crates/civ/src/ic7300.rs:772`](https://github.com/robinonsay/cw-message-gateway/blob/44185fa9a00369c379d9d8af40ca307e3867e860/crates/civ/src/ic7300.rs#L772)).
- **Duty cycle, keying watchdog, stuck margin**: the share of time a transmitter is keyed; the node's limit on how long one keying may last; and the time allowed past a piece's expected end before the radio is taken to be stuck on transmit. See [05 Node loop and station safety](05-node-loop-station-safety.md).
- **Inhibit file**: the node's transmit inhibit, a latch kept in the file `tx-inhibited`; while it exists the node does not transmit.

## How it works

### Three kinds of build

The repository holds three kinds of build that share some source but not a build system.

1. **The host workspace** (the root `Cargo.toml`). It builds `hfnode` and the five libraries it uses, with stable Rust, for Linux (x86-64, and aarch64 for a Raspberry Pi), macOS (Apple Silicon and Intel) and Windows. Every member takes `edition` and `license` from `[workspace.package]` ([`Cargo.toml:5-8`](https://github.com/robinonsay/cw-message-gateway/blob/44185fa9a00369c379d9d8af40ca307e3867e860/Cargo.toml#L5-L8)). There is no `rust-toolchain.toml` at the root, so a developer's own stable compiler is used (the README asks for "a Rust toolchain (stable)", [`README.md:91-95`](https://github.com/robinonsay/cw-message-gateway/blob/44185fa9a00369c379d9d8af40ca307e3867e860/README.md#L91-L95)).
2. **The firmware workspaces.** Each Pico 2 image is its own Cargo workspace: its `Cargo.toml` has an empty `[workspace]` table, "it builds only for the RP2350 ... so it is not a member of the hfnode workspace" ([`firmware/pico2-keyer/Cargo.toml:9-11`](https://github.com/robinonsay/cw-message-gateway/blob/44185fa9a00369c379d9d8af40ca307e3867e860/firmware/pico2-keyer/Cargo.toml#L9-L11)). Each has its own `Cargo.lock`, its own pinned compiler (`rust-toolchain.toml`), edition 2024, and its target, `thumbv8m.main-none-eabihf` (Cortex-M33 with hardware floating point, no operating system), set in `.cargo/config.toml` together with the linker script `link.ld` ([`firmware/pico2-keyer/.cargo/config.toml:1-7`](https://github.com/robinonsay/cw-message-gateway/blob/44185fa9a00369c379d9d8af40ca307e3867e860/firmware/pico2-keyer/.cargo/config.toml#L1-L7)). rustos's `pico2` crate puts `link.ld` on the linker's search path from its build script ([`firmware/pico2/build.rs:14-18`](https://github.com/robinonsay/rustos/blob/80bf5998a60a41b3741041062ff7e9c59caf95b2/firmware/pico2/build.rs#L14-L18)). A firmware workspace reaches into the host workspace's crates by path (`keyer-core` on main; `decoder-core` in PRs #30 and #31, which brings `cw` and `libm` with it) and into rustos by a git revision.
3. **Builds that are not Rust.** The UV-K1 handheld image is C: `firmware/uv-k1/build.sh` fetches the upstream NR7Y firmware at a fixed commit, applies a patch, adds `hfnode`'s files and builds it with CMake, Ninja and `arm-none-eabi-gcc` ([`firmware/uv-k1/build.sh:16-17`](https://github.com/robinonsay/cw-message-gateway/blob/44185fa9a00369c379d9d8af40ca307e3867e860/firmware/uv-k1/build.sh#L16-L17)). That route is parked: "nothing here is to be flashed onto a radio" ([`docs/handheld.md:3-7`](https://github.com/robinonsay/cw-message-gateway/blob/44185fa9a00369c379d9d8af40ca307e3867e860/docs/handheld.md#L3-L7)). The enclosure is an OpenSCAD model that `hardware/keyer-box/render.sh` renders and fit-checks by hand; CI does not run it.

### `no_std` crates and why

Three crates are written to build without the standard library, because the same code runs on the Pico 2 and in `hfnode`'s tests:

| Crate | How it is `no_std` | Why |

Two consequences matter day to day. First, the host and the firmware are linted by different `clippy` versions: a host change is checked by whatever stable is current on the runner, and a new stable release can add lints that turn the host jobs red with no code change. A project note from 2026-10-11 records CI's stable as 1.99 at that time; the repository itself does not say. Run `cargo +stable clippy` before pushing host changes. Second, the firmware compiler is part of the firmware's identity: "a different compiler is a different firmware" ([`firmware/pico2-keyer/rust-toolchain.toml:1-4`](https://github.com/robinonsay/cw-message-gateway/blob/44185fa9a00369c379d9d8af40ca307e3867e860/firmware/pico2-keyer/rust-toolchain.toml#L1-L4)).

### What CI runs

![The CI jobs as boxes with their runners and main steps and what each guards: the Linux test job, the macOS and Windows matrix with the self-test, the Raspberry Pi aarch64 check, the keyer firmware job with its safety checks and artifact, the handheld host test and firmware build; PR #30 adds a decoder-core step and the decoder firmware job, PR #31 adds the core 1 check](diagrams/02-ci-pipeline.svg)

*Figure: every job runs on every push and every pull request; red steps are the firmware's safety checks, and purple is not on main yet.*

The workflow has one file and no job dependencies (no `needs:`), so all jobs start together. It runs on `push` (any branch) and on `pull_request` ([`.github/workflows/ci.yml:3-5`](https://github.com/robinonsay/cw-message-gateway/blob/44185fa9a00369c379d9d8af40ca307e3867e860/.github/workflows/ci.yml#L3-L5)). A branch with an open PR is therefore built twice for each push: once as the branch head (the push run) and once as GitHub's merge of the branch into its base (the pull_request run; this is GitHub's behaviour, not something the workflow sets). The two runs build firmware from different commits, so their UF2 files carry different build ids and differ in bytes. The audit's records name push runs: the keyer file of run 37778418801 (a push to main at `eef8c12`), the decoder box file of run 38142799453 and the one-Pico keyer image of run 38146719691 (pushes to the PR #30 and PR #31 branches). These were read from the GitHub API on 2026-10-13.

Artifacts belong to a job, not to the run's overall result. Run 37778418801, whose keyer artifact is the audited one, is marked "failure" overall because its Windows job failed; its keyer job passed (GitHub API, 2026-10-13).

### The build-id handshake

The firmware learns which commit it was built from at compile time, and `hfnode` can check it at run time. The host half (how `hfnode` opens the box and parses `HELLO`) is on [09 Keyer box: host side](09-keyer-host-side.md).

0. Before any build check, `hfnode` checks the box's protocol version, the first field of `HELLO`, as it opens the box (`check_hello`, called from [`crates/hfnode/src/keyer/rig.rs:203`](https://github.com/robinonsay/cw-message-gateway/blob/44185fa9a00369c379d9d8af40ca307e3867e860/crates/hfnode/src/keyer/rig.rs#L203)). `main` accepts only `keyer_core::VERSION` = 4 ([`crates/hfnode/src/keyer.rs:387`](https://github.com/robinonsay/cw-message-gateway/blob/44185fa9a00369c379d9d8af40ca307e3867e860/crates/hfnode/src/keyer.rs#L387), [`crates/keyer-core/src/lib.rs:26`](https://github.com/robinonsay/cw-message-gateway/blob/44185fa9a00369c379d9d8af40ca307e3867e860/crates/keyer-core/src/lib.rs#L26)). PR #31 (draft, not on main) sets `VERSION` to 5 ([`crates/keyer-core/src/lib.rs:29`](https://github.com/robinonsay/cw-message-gateway/blob/bc5062ae4f56ae1f9949b3b067218c7e675d88f8/crates/keyer-core/src/lib.rs#L29)) and makes `hfnode` accept `VERSIONS: [u32; 2] = [4, keyer_core::VERSION]` ([`crates/hfnode/src/keyer.rs:386`](https://github.com/robinonsay/cw-message-gateway/blob/bc5062ae4f56ae1f9949b3b067218c7e675d88f8/crates/hfnode/src/keyer.rs#L386), checked at [`crates/hfnode/src/keyer.rs:399`](https://github.com/robinonsay/cw-message-gateway/blob/bc5062ae4f56ae1f9949b3b067218c7e675d88f8/crates/hfnode/src/keyer.rs#L399)). So a box flashed with PR #31's image needs an `hfnode` built from a commit that includes #31; `main`'s `hfnode` refuses it (the audit says the same, `audit/report.md` §3, "PR #31 re-checked").
1. CI writes `KEYER_BUILD_ID=$(git rev-parse --short=8 HEAD)` into the job's environment and runs `build.sh` ([`.github/workflows/ci.yml:177-180`](https://github.com/robinonsay/cw-message-gateway/blob/44185fa9a00369c379d9d8af40ca307e3867e860/.github/workflows/ci.yml#L177-L180)). `build.sh` itself sets `KEYER_BUILD_ID` from the commit it builds ([`firmware/pico2-keyer/build.sh:19-22`](https://github.com/robinonsay/cw-message-gateway/blob/44185fa9a00369c379d9d8af40ca307e3867e860/firmware/pico2-keyer/build.sh#L19-L22), [`firmware/pico2-keyer/build.sh:34`](https://github.com/robinonsay/cw-message-gateway/blob/44185fa9a00369c379d9d8af40ca307e3867e860/firmware/pico2-keyer/build.sh#L34)).
2. `build.rs` tells cargo to rebuild when `KEYER_BUILD_ID` changes, so a cached build cannot keep an old id ([`firmware/pico2-keyer/build.rs:1-6`](https://github.com/robinonsay/cw-message-gateway/blob/44185fa9a00369c379d9d8af40ca307e3867e860/firmware/pico2-keyer/build.rs#L1-L6)).
3. The firmware reads it with `option_env!`; a build without it reports `-` ([`firmware/pico2-keyer/src/main.rs:95-101`](https://github.com/robinonsay/cw-message-gateway/blob/44185fa9a00369c379d9d8af40ca307e3867e860/firmware/pico2-keyer/src/main.rs#L95-L101)), and hands it to the shared rules with `Keyer::with_build` ([`firmware/pico2-keyer/src/main.rs:229`](https://github.com/robinonsay/cw-message-gateway/blob/44185fa9a00369c379d9d8af40ca307e3867e860/firmware/pico2-keyer/src/main.rs#L229)). `with_build` accepts one word of 1 to 12 letters, digits, `.`, `-` or `_`, and reports `?` for anything else ([`crates/keyer-core/src/keyer.rs:447-457`](https://github.com/robinonsay/cw-message-gateway/blob/44185fa9a00369c379d9d8af40ca307e3867e860/crates/keyer-core/src/keyer.rs#L447-L457)).
4. The box reports it as the tenth field of `OK HELLO ...` ([`crates/keyer-core/src/keyer.rs:24`](https://github.com/robinonsay/cw-message-gateway/blob/44185fa9a00369c379d9d8af40ca307e3867e860/crates/keyer-core/src/keyer.rs#L24)).
5. `hfnode` reads `[keyer] firmware_build`, declared as `firmware_build: Option<String>` with no default ([`crates/hfnode/src/config.rs:121-124`](https://github.com/robinonsay/cw-message-gateway/blob/44185fa9a00369c379d9d8af40ca307e3867e860/crates/hfnode/src/config.rs#L121-L124)). If it is set, config validation refuses an empty value, more than 12 characters, whitespace, and `-` (which every working-tree build reports) ([`crates/hfnode/src/keyer.rs:330-342`](https://github.com/robinonsay/cw-message-gateway/blob/44185fa9a00369c379d9d8af40ca307e3867e860/crates/hfnode/src/keyer.rs#L330-L342)), and every time `hfnode` opens the box it compares the two exactly and refuses a mismatch ([`crates/hfnode/src/keyer.rs:441-451`](https://github.com/robinonsay/cw-message-gateway/blob/44185fa9a00369c379d9d8af40ca307e3867e860/crates/hfnode/src/keyer.rs#L441-L451), called from [`crates/hfnode/src/keyer/bench.rs:115-119`](https://github.com/robinonsay/cw-message-gateway/blob/44185fa9a00369c379d9d8af40ca307e3867e860/crates/hfnode/src/keyer/bench.rs#L115-L119)). **If it is unset, no build check is made and any build is accepted**, a working-tree `-` build included (`check_build` returns `Ok` for `None`). Set it to the audited build id after flashing ([docs/keyer.md](../keyer.md), "Flashing the firmware"; [14 Audit, bench and flashing](14-audit-bench-flashing.md)).

`git rev-parse --short=8` prints at least eight characters, and more only if eight are ambiguous in the repository (git's rule); both ends allow up to 12.

The decoder box (PR #30) reports `DECODER_BUILD_ID` in its own `HELLO` the same way, but nothing in `hfnode` checks it: PR #30 has no host side for the box, and the not-yet-opened PR 4 (project files, `design/pico-decoder-pr4.patch`) only logs the build it reads.

## Algorithms and processing

### The reproducible keyer build (`build.sh`)

Step by step ([`firmware/pico2-keyer/build.sh:19-40`](https://github.com/robinonsay/cw-message-gateway/blob/44185fa9a00369c379d9d8af40ca307e3867e860/firmware/pico2-keyer/build.sh#L19-L40)):

1. Find the script's directory and the repository root; take COMMIT (default `HEAD`); compute `id = git rev-parse --short=8 COMMIT`.
2. Delete and recreate `/tmp/pico2-keyer-build`, and unpack `git archive COMMIT` into it. Only committed files are built: uncommitted edits are not in the UF2.
3. Unset `RUSTFLAGS`, `CARGO_ENCODED_RUSTFLAGS`, `CARGO_BUILD_RUSTFLAGS`, `CARGO_TARGET_DIR`, `CARGO_BUILD_TARGET_DIR`. Other settings in the caller's environment can still change a local build; see "Limits" below.
4. From inside the unpacked `firmware/pico2-keyer` (so that rustup takes its `rust-toolchain.toml`), run `KEYER_BUILD_ID=$id cargo build --release --locked`.
5. Copy the ELF next to the script as `pico2-keyer.elf`, run the unpacked commit's own `uf2.py` on it, and write the SHA-256 with Python's `hashlib` in `sha256sum` format.
6. Print `build id <id>, <n> bytes, UF2 SHA-256 <hash>`.

Why the fixed path: `keyer-core` is outside the firmware's Cargo workspace, and "cargo mixes the absolute path of such a dependency into the hash in every symbol name; the order the code is laid out in follows those names, so a plain `cargo build` of one commit in two checkouts can give two different UF2s" ([`firmware/pico2-keyer/build.sh:9-14`](https://github.com/robinonsay/cw-message-gateway/blob/44185fa9a00369c379d9d8af40ca307e3867e860/firmware/pico2-keyer/build.sh#L9-L14)). Two `build.sh` runs at once would share the path, so run one at a time. The decoder box's `build.sh` (PR #30) is the same with `/tmp/pico2-decoder-build` and `DECODER_BUILD_ID`, and uses the keyer's `uf2.py` from the same commit ([`firmware/pico2-decoder/build.sh:23-38`](https://github.com/robinonsay/cw-message-gateway/blob/3efaf842e1aab75354e5e19d0384a703d4d786be/firmware/pico2-decoder/build.sh#L23-L38)).

On Linux, `build.sh` gives CI's file byte for byte. [`firmware/pico2-keyer/README.md:49-55`](https://github.com/robinonsay/cw-message-gateway/blob/44185fa9a00369c379d9d8af40ca307e3867e860/firmware/pico2-keyer/README.md#L49-L55) says a Mac build has never been compared with CI's. One has since matched: `build.sh eef8c12` on a Mac printed the audited SHA-256 (`bench/quansheng.md`, results 2026-10-09 16:10Z, project files). A match proves the download is what the commit builds to; a difference proves nothing; only CI's download, matched to the audit's hash, is flashed ([14 Audit, bench and flashing](14-audit-bench-flashing.md)).

### Why the bytes change with no source change

Three things can change the UF2 without a change to the firmware's Rust source (the build id always does), and a commit that carries any of them goes to the audit again:

- **The build id.** It is a string in the image, so every commit's build differs from every other's. A project note records that two builds of the same tree with different ids differed in 18 bytes (the id string and one 8-byte table swapped places, and two instructions changed).
- **The rustos pin.** "Moving this pin can change the UF2 with no source change, since cargo mixes the commit into the crate hashes that order the code" ([`firmware/pico2-keyer/Cargo.toml:26-29`](https://github.com/robinonsay/cw-message-gateway/blob/44185fa9a00369c379d9d8af40ca307e3867e860/firmware/pico2-keyer/Cargo.toml#L26-L29)). The project note `rustos-template-cargo-error.md` records the case that proved it: pinning rustos #4's branch commit `6b02215`, whose tree is identical to master's merge `8c91507`, moved 46,030 bytes; pinning `8c91507` itself, built with the audited build id, gave the audited file byte for byte. Rebuild at the audited build id and compare; never assume either way.
- **The compiler, the profiles, `.cargo/config.toml`, `uf2.py`, any path dependency** (`keyer-core`; with PR #31 also `decoder-core` and `cw`), **the root `Cargo.toml`'s `[workspace.package]`** (the path crates take `edition.workspace = true` from it, [`crates/keyer-core/Cargo.toml:5`](https://github.com/robinonsay/cw-message-gateway/blob/44185fa9a00369c379d9d8af40ca307e3867e860/crates/keyer-core/Cargo.toml#L5), [`Cargo.toml:5-8`](https://github.com/robinonsay/cw-message-gateway/blob/44185fa9a00369c379d9d8af40ca307e3867e860/Cargo.toml#L5-L8); `git archive` unpacks it and cargo reads it when it builds the firmware), **and any other locked dependency** in the firmware's `Cargo.lock` (for example `libm` in PR #31).

This is why the file flashed is the artifact of the run the audit named, not "the latest build", and not a local build.

### ELF to UF2 (`uf2.py`)

`uf2.py` does what `picotool uf2 convert` does for a plain image with no partition table, so the build needs only Python ([`firmware/pico2-keyer/uf2.py:11-19`](https://github.com/robinonsay/cw-message-gateway/blob/44185fa9a00369c379d9d8af40ca307e3867e860/firmware/pico2-keyer/uf2.py#L11-L19)).

1. **Load** (`load_segments`, [`firmware/pico2-keyer/uf2.py:49-77`](https://github.com/robinonsay/cw-message-gateway/blob/44185fa9a00369c379d9d8af40ca307e3867e860/firmware/pico2-keyer/uf2.py#L49-L77)): require a 32-bit little-endian Arm ELF (`EM_ARM` = 40); take each `PT_LOAD` segment with file size > 0 at its physical (load) address; refuse any byte outside the Pico 2's flash, `0x10000000` to `0x10000000 + 4 MB`.
2. **Page** (`pages`, [`firmware/pico2-keyer/uf2.py:80-88`](https://github.com/robinonsay/cw-message-gateway/blob/44185fa9a00369c379d9d8af40ca307e3867e860/firmware/pico2-keyer/uf2.py#L80-L88)): split into 256-byte pages keyed by address; gaps inside a page are zeros.
3. **Check** (`check_image`, [`firmware/pico2-keyer/uf2.py:91-109`](https://github.com/robinonsay/cw-message-gateway/blob/44185fa9a00369c379d9d8af40ca307e3867e860/firmware/pico2-keyer/uf2.py#L91-L109)): the first page must exist and start with an Arm vector table: the initial stack pointer must be above `0x20000000`, at most `0x20082000` (the top of 520 kB of SRAM) and 8-byte aligned; the reset handler must have its Thumb bit set and land in a page of the image; and an `IMAGE_DEF` block (start marker `0xFFFFDED3` followed later by end marker `0xAB123579`) must be in the first 4 kB, without which "the RP2350 would not boot it".
4. **Write** (`uf2`, [`firmware/pico2-keyer/uf2.py:112-129`](https://github.com/robinonsay/cw-message-gateway/blob/44185fa9a00369c379d9d8af40ca307e3867e860/firmware/pico2-keyer/uf2.py#L112-L129)): one 512-byte block per page: eight 32-bit little-endian header words (magic `0x0A324655`, `0x9E5D5157`, flags `0x00002000` = family ID present, target address, payload size 256, block number, block count, family `0xE48BFF59` = `rp2350-arm-s`), the 256 data bytes padded with zeros to 476, and the end magic `0x0AB16F30` ([`firmware/pico2-keyer/uf2.py:25-39`](https://github.com/robinonsay/cw-message-gateway/blob/44185fa9a00369c379d9d8af40ca307e3867e860/firmware/pico2-keyer/uf2.py#L25-L39)).

### Build and check the keyer firmware


### Check a downloaded artifact before it goes near a box

1. Take the artifact of the run the audit names, not the newest run: `audit/final-grades.md`, "The file to flash", for the keyer box file and the one-Pico image; `audit/report.md` §3, "PR #30 re-checked", for the decoder box file (project files).
2. Download it and hash `pico2-keyer.uf2`: `sha256sum` on Linux, `shasum -a 256` on a Mac. With the GitHub CLI, for the keyer box file of run 37778418801:

   ```sh
   gh run download 37778418801 -R robinonsay/cw-message-gateway \
     -n pico2-keyer-firmware -D keyer-eef8c126      # gh unzips it into that folder
   sha256sum keyer-eef8c126/pico2-keyer.uf2          # shasum -a 256 ... on a Mac
   gh run view 37778418801 -R robinonsay/cw-message-gateway --log | grep 'UF2 SHA-256'
   ```

   The last line reads the build id, size and hash that `build.sh` printed in that run's log.
3. Compare with the audit's hash, not with the `.sha256` in the zip or the run's log, which come from the same run. If they differ, do not flash it.
4. Flashing, the replug, `[keyer] firmware_build` and `hfnode keyer --config C check` are in [docs/keyer.md](../keyer.md), "Flashing the firmware" ([`docs/keyer.md:121-166`](https://github.com/robinonsay/cw-message-gateway/blob/44185fa9a00369c379d9d8af40ca307e3867e860/docs/keyer.md#L121-L166)), and on [14 Audit, bench and flashing](14-audit-bench-flashing.md). Nothing is flashed or keyed until the audit has posted the hash and Robin says go.

### Work on the firmware against a local rustos checkout

From `firmware/pico2-keyer`, with rustos cloned beside this repository ([`firmware/pico2-keyer/README.md:67-73`](https://github.com/robinonsay/cw-message-gateway/blob/44185fa9a00369c379d9d8af40ca307e3867e860/firmware/pico2-keyer/README.md#L67-L73)):

```sh
cargo build --release \
  --config 'patch."https://github.com/robinonsay/rustos".api.path="../../../rustos/api"' \
  --config 'patch."https://github.com/robinonsay/rustos".pico2.path="../../../rustos/firmware/pico2"'
```

This is for development only: the result reports build `-`, which `hfnode` refuses as a `firmware_build` value. It also rewrites the `api` and `pico2` entries of `firmware/pico2-keyer/Cargo.lock` to the local paths. Restore the lock with `git checkout -- firmware/pico2-keyer/Cargo.lock` before committing: a committed lock with path entries fails CI's `cargo clippy --release --locked` and no longer names a rustos revision. Only a `rev` change in `Cargo.toml` with the lock cargo regenerates from it is ever committed.

To ship a rustos change, open it as a rustos PR (base `master`), pin the firmware at that PR's head commit, and then, once it merges, at `master`'s merge commit: the firmware is "pinned in `Cargo.toml` at a commit on a rustos branch until its PRs merge, then at their merge commits" ([`firmware/pico2-keyer/README.md:16-17`](https://github.com/robinonsay/cw-message-gateway/blob/44185fa9a00369c379d9d8af40ca307e3867e860/firmware/pico2-keyer/README.md#L16-L17)). PR #31 is at the first step: it pins `410dffa`, rustos PR #6's head. Each time, change the `rev` of both `api` and `pico2`, let cargo update `Cargo.lock` (both `source` lines change), commit both, and send each new head to the audit.

### Add a crate to the workspace

1. Create `crates/<name>/Cargo.toml` with `edition.workspace = true` and `license.workspace = true`, and add the path to `members` in the root `Cargo.toml`.
2. If firmware will use it, make it `#![cfg_attr(not(test), no_std)]` with no allocator, as `keyer-core` and `decoder-core` are, and add a CI step that runs `cargo clippy` and `cargo build` for `thumbv8m.main-none-eabihf`, as PR #30 did for `decoder-core` ([`.github/workflows/ci.yml:49-56`](https://github.com/robinonsay/cw-message-gateway/blob/3efaf842e1aab75354e5e19d0384a703d4d786be/.github/workflows/ci.yml#L49-L56)). `cargo test --all` alone never builds it without `std`.

## Changing it

### Branches and pull requests

- `main` is the default branch on GitHub (the API reported `main` on 2026-10-13). rustos's is `master`.
- One branch per working thread, named like `claude/<topic>-<suffix>` so far. After its PR merges, the branch is restarted from `main` for the thread's next change, under the same name: `claude/pico-decoder-u9bum5` carried PR #28 (merge `e8450dc`) and now carries PR #30; `claude/nr7y-docs-pkhb3g` carried #25 (`b4ec641`) and #26 (`afdb802`). A stacked PR gets a branch of its own.
- PRs target `main`. A PR that builds on an unmerged one (stacked) targets that PR's branch and is retargeted to `main` when the lower one merges: PR #31's base is `claude/pico-decoder-u9bum5`, PR #30's branch. rustos PRs target `master`.
- A PR stays a draft while it is still changing. Robin (the project owner) merges every PR, sometimes before a review has finished; Claude never merges. Merges are merge commits ("Merge pull request #29 ...").
- Any PR that touches keying, CI-V or a firmware image goes to the safety audit before it merges, and every new head commit of such a PR needs a fresh review (and a new hash for a firmware image). See [14 Audit, bench and flashing](14-audit-bench-flashing.md).

### Rules that never change

- **Never lower the CI time scale (20x), never widen a timeout, never loosen or delete a test, and never push an empty commit to get a green run.** A failure in a timing test is re-run once (see below); a failure that repeats is treated as a bug until shown otherwise.
- Never remove or weaken `check_faults.py`, `check_pins.py`, `check_core1.py`, their `--self-test` runs, the path-independence `cmp`, `--locked`, or the SHA-256 output.
- The firmware compiler stays pinned, and the CI `toolchain:` input matches `rust-toolchain.toml`.
- The file flashed onto either box is the CI artifact of the run the audit named, byte-identical to the audit's hash. Never a local build, and never a newer run's file.
- The box's limits and gates are not set here; they are listed with their code lines on [13 Safety rules](13-safety-rules.md), and nothing on this page changes them.

### Which tests to update

- A change to `crates/cw`'s non-`std` code: the two `cw` steps of the test job cover it; add tests that pass under `--cfg cw_force_libm` too.
- A change to a firmware image: `cargo clippy --release --locked` in its directory, `build.sh`, and the checker scripts. If you change lines that `mutants.py` or `mutants_core1.py` edit, update their strings in the same PR and run them by hand.
- A change to timing in the node or a mock: run `cargo test --all` with `HFNODE_E2E_SCALE=20` and with it unset, and `hfnode selftest --scale 20`; see [12 Testing](12-testing.md).

## Known bugs, limits and flakes

### Known CI flakes

These failures come from GitHub's shared runners holding up the test process or one of its threads, which the wall-clock tests cannot tell from a slow node. The rule for all of them: look at the failing check first, re-run the failed job once (`gh run rerun <run-id> -R robinonsay/cw-message-gateway --failed`), and never lower the scale, widen a timeout or loosen the test.

| Mock IC-7300 scenarios on macOS (`wx_last`) | Two `17 FF` sent, the reply never keyed | Not explained (project notes `station-thread-stall-watchdog.md`, `tune-flag-race-pr.md`). Fail-safe. | None. |

One family of "flakes" was a real bug: Windows IC-7300 scenarios cut with "17 FF sent 4 times" and the pause meter at 0.00 s were a duty-file write timed as keying, fixed in PRs #21 and #22 (project note `station-thread-stall-watchdog.md`). That is why a repeating failure is investigated, not re-run until green.

The full flake table, with the pause meters and the regression tests, is on [12 Testing](12-testing.md); this table is the CI view of it and the two should say the same.

### Limits

- The host toolchain is not pinned, so a new stable compiler or `clippy` can turn the host jobs red with no code change.
- `check-pi` and the Intel Mac step only compile; nothing runs on aarch64 or x86-64 macOS in CI.
- `build.sh` is checked to reproduce CI's UF2 on Linux, where CI builds every commit twice and compares. On a Mac one build has matched (`build.sh eef8c12` printed the audited SHA-256; `bench/quansheng.md`, results 2026-10-09 16:10Z, project files); nothing compares Mac builds routinely. [`firmware/pico2-keyer/README.md:49-55`](https://github.com/robinonsay/cw-message-gateway/blob/44185fa9a00369c379d9d8af40ca307e3867e860/firmware/pico2-keyer/README.md#L49-L55) and [`docs/keyer.md:161-163`](https://github.com/robinonsay/cw-message-gateway/blob/44185fa9a00369c379d9d8af40ca307e3867e860/docs/keyer.md#L161-L163) are stale on this: they still say a Mac build has never been compared.
- The mutation scripts are not in CI, and rustos has no CI of its own: its code is built and checked in CI only as a dependency of the firmware jobs.
- `check_faults.py` follows calls only two deep and fails on any branch before the key-opening store, so a refactor of `safe_state` that adds a branch fails CI by design ([`firmware/pico2-keyer/check_faults.py:118-131`](https://github.com/robinonsay/cw-message-gateway/blob/44185fa9a00369c379d9d8af40ca307e3867e860/firmware/pico2-keyer/check_faults.py#L118-L131)).
- `check_core1.py` cannot run without `firmware/pico2-decoder/check_pins.py` beside it ([`firmware/pico2-keyer/check_core1.py:57-69`](https://github.com/robinonsay/cw-message-gateway/blob/bc5062ae4f56ae1f9949b3b067218c7e675d88f8/firmware/pico2-keyer/check_core1.py#L57-L69)); moving or deleting the decoder firmware directory breaks the keyer job in PR #31.
- PR #31 pins rustos at a commit that is only on rustos PR #6's branch. Keep that branch until the pin moves to master's merge; whether cargo could fetch the commit after the branch is deleted was not checked.
- Audited artifacts expire (dates above).
- `build.sh` clears only `RUSTFLAGS`, `CARGO_ENCODED_RUSTFLAGS`, `CARGO_BUILD_RUSTFLAGS`, `CARGO_TARGET_DIR` and `CARGO_BUILD_TARGET_DIR` ([`firmware/pico2-keyer/build.sh:30-32`](https://github.com/robinonsay/cw-message-gateway/blob/44185fa9a00369c379d9d8af40ca307e3867e860/firmware/pico2-keyer/build.sh#L30-L32)), although its comment says "Nothing in the caller's environment may change what is built". `RUSTUP_TOOLCHAIN` (which overrides `rust-toolchain.toml`), `CARGO_PROFILE_RELEASE_*`, `CARGO_TARGET_THUMBV8M_MAIN_NONE_EABIHF_RUSTFLAGS`, `RUSTC`, `RUSTC_WRAPPER`, and a cargo config file in `$CARGO_HOME` or in `/tmp/.cargo/` (an ancestor of `/tmp/pico2-keyer-build`) still apply. Before comparing a local build with the audit's hash, run it with none of them set; otherwise a mismatch on Linux can be a false alarm.
- The host jobs build without `--locked` ([`.github/workflows/ci.yml:30-33`](https://github.com/robinonsay/cw-message-gateway/blob/44185fa9a00369c379d9d8af40ca307e3867e860/.github/workflows/ci.yml#L30-L33), [`.github/workflows/ci.yml:80-93`](https://github.com/robinonsay/cw-message-gateway/blob/44185fa9a00369c379d9d8af40ca307e3867e860/.github/workflows/ci.yml#L80-L93), [`.github/workflows/ci.yml:136`](https://github.com/robinonsay/cw-message-gateway/blob/44185fa9a00369c379d9d8af40ca307e3867e860/.github/workflows/ci.yml#L136)), so CI does not catch a stale root `Cargo.lock`: cargo re-resolves on the runner, while the README's `cargo install --locked` would then fail. Run `cargo test --locked --all` before pushing a dependency change. Only the firmware jobs enforce their lockfiles.
- `check_faults.py` has no `--self-test`: its `main` takes exactly one ELF ([`firmware/pico2-keyer/check_faults.py:140-154`](https://github.com/robinonsay/cw-message-gateway/blob/44185fa9a00369c379d9d8af40ca307e3867e860/firmware/pico2-keyer/check_faults.py#L140-L154)). CI never shows it failing a broken image, unlike `check_pins.py` and `check_core1.py`.
- Actions and runner images are referenced by moving tags, not commit SHAs: `actions/checkout@v4`, `dtolnay/rust-toolchain@stable` and `@master`, `Swatinem/rust-cache@v2`, `actions/upload-artifact@v4`, and the `*-latest` runners. The firmware bytes do not depend on them (`build.sh` uses rustup and `rust-toolchain.toml`), but the host jobs can change behaviour with no commit.
